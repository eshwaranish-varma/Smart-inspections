Smart Inspection Platform

End-to-End Technical Architecture: From Raw Inspection Inputs to Grounded FDA 483 Observations and Evaluation Dashboards

This browser-ready architecture view is designed for client presentations. It shows how the project takes raw end-user evidence, routes it through src/gui and backend handlers, grounds AI output against source text, resolves CFR and IOM references, computes evaluation metrics, and exposes explainable outputs to reviewers and decision-makers.

Primary Technical Story

The project does not directly generate a narrative from a raw file. It first extracts text, consolidates notes, segments distinct issues, retrieves the most relevant evidence and regulatory references using embeddings, drafts one observation per issue, validates the observation against source text and CFR records, scores it, stores the full trace, and then presents the results in evaluation dashboards.

Business Assurance

Traceable: every observation points back to evidence and pipeline events.

Grounded: evidence is checked against raw notes by substring and semantic similarity.

Auditable: workflow logs, AI run logs, and pipeline run logs are all stored.

Actionable: dashboards surface quality, risk, and remediation signals per inspection.

2. Step-by-Step Technical Process

This section is designed for a verbal walkthrough. It explains each stage in project terms, from the user interface to the backend AI route and the evaluation response.

01

End user submits inspection evidence

The investigator enters typed notes, uploads documents, and optionally marks checklist evidence.

02

OCR normalizes non-machine-readable evidence

PDF and image sources are converted to readable text so they can participate in downstream grounding.

03

src/gui assembles the final raw_notes

Typed notes, OCR text, and checklist evidence are merged into one canonical source block.

04

Next.js workflow route validates and forwards

The route handler checks workflow permissions and forwards the request to the backend AI route.

05

FastAPI creates pipeline run metadata

The backend opens a pipeline run record so the full generation lifecycle can be audited later.

06

LLM segmentation isolates distinct issues

Raw notes are split into distinct observations so the project preserves one issue to one draft row.

07

Embeddings retrieve relevant context

Each segmented issue is used as a query against note chunks and regulatory knowledge-base chunks.

08

LLM drafts one grounded 483 observation

The backend drafts exactly one observation per issue, carrying evidence and proposed CFR citation.

09

CFR and grounding validation executes

The system checks whether the evidence is anchored in the source and whether the CFR citation resolves.

10

Metrics, confidence, and status are computed

Each observation receives evaluation scores, a confidence breakdown, and a pass or warning status.

11

Evaluation and trace data are persisted

The project writes evaluation logs, pipeline trace rows, and workflow AI run linkage rows.

12

Dashboards surface quality and explainability

Reviewers see inspection-level quality scores and can drill into the exact evidence and retrieval path.

Why this architecture satisfies a client

It is explainable. The client can see input, segmentation, retrieval, CFR candidates, output, and scoring.

It is measurable. The project calculates grounding quality rather than assuming the narrative is correct.

It is workflow-aware. The `src/gui` route layer enforces inspection context and stores business audit linkage.

It is enterprise-friendly. The design separates user workflow, AI orchestration, regulatory retrieval, and audit storage.

Client message

The platform is not simply "an LLM writing observations." It is a governed inspection pipeline that extracts evidence, grounds AI output, validates regulations, and exposes quality controls before the narrative influences compliance or remediation decisions.

3. Technical Grounding Architecture

This strip shows how the AI-generated observation is grounded back to evidence, CFR citations, and IOM or regulatory references in project terms.

Canonical Source Text

The platform begins with one canonical raw_notes block assembled from typed notes and OCR text.

Segment Query

Each segmented issue becomes a retrieval query so the platform only searches for evidence relevant to that issue.

Embedding Retrieval

Note chunks are embedded and scored by cosine similarity. Knowledge-base PDF chunks are also retrieved.

Observation Draft

The LLM drafts a single observation with evidence lines and a proposed CFR citation for that issue.

Validation Layer

Evidence is checked against source text with substring, semantic, or hybrid grounding. CFR is matched against Title 21 references.

Explainable Output

The final record carries evidence sources, citation match scores, grounding F1, narrative overlap, and confidence.

Evidence Grounding

The project verifies whether each evidence string can be tied back to the source notes. This prevents polished but unsupported narratives from being treated as trusted inspection findings.

CFR Grounding

Proposed CFR citations are checked through exact, fuzzy, semantic, or hybrid matching against Title 21 reference data before they are presented as validated.

IOM and Regulatory Context

The knowledge base provides retrieval context from regulatory PDFs so narrative generation is informed by reference material rather than only the raw note text.

4. Database and Traceability Model

The project stores different levels of traceability for different reporting needs: workflow linkage, explainable AI trace, and inspection evaluation history.

Workflow Layer in src/gui

inspections stores inspection state and draft payloads.

ai_runs stores high-level workflow AI calls and links to pipeline_run_id.

audit_logs stores business actions such as generate, review, approve, or return.

Backend Explainability Layer

pipeline_runs stores one row per generation run.

pipeline_run_events stores segmentation, retrieval, grounding, evaluation, and storage events.

pipeline_run_chunks, pipeline_run_cfr_matches, and pipeline_run_observations store observation-level explainability.

Evaluation Layer

evaluation_logs.json stores the final input, output, and scoring bundle used by the inspection evaluation dashboard.

This is the quality and score history the client sees per inspection.

Business interpretation

A weakly grounded narrative is visibly flagged before it reaches that decision stage.
